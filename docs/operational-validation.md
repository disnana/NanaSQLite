## 再監査で見つけて修正した問題

前回の検証には不足があった。実ファイルのDBと公開APIを使って以下の失敗を再現し、修正後に成功することを確認した。

- 全件キャッシュヒット時だけ `batch_get()` が読み取りフックを飛ばしていた。非同期・unbounded・LRU・TTLで結果の一貫性を検査した。
- 別のSQLite接続が書込みロックを保持すると、v2の失敗行復旧で未開始トランザクションをROLLBACKし、後続の失敗行がDLQに入らなかった。開始済みの場合だけROLLBACKし、全行を再投入して独立接続で永続化結果を確認した。
- 古いDLQ項目の再試行が、新しい保存待ち・保存済みの値や削除を上書きしていた。同じテーブル・キーの新しいKVS操作を優先し、失敗公開・再投入・新規受付を同じロック順で同期した。任意SQLにはこのキー単位の保護は適用しない。
- 受付上限なしの非同期書込みは、呼出元のキャンセル後に `close()` すると保存が失われる可能性があった。上限の有無によらず実際のworker完了を追跡して終了時に待つ。
- 未完了トランザクションで `close()` が失敗すると、その後のロールバックも受付拒否されていた。失敗した終了状態を解除し、ロールバックして再度終了できるようにした。

追加の実動作試験には、別プロセスによる更新・削除・新規挿入、分割走査の0件/境界件数/日本語値/キー順、非同期イテレータの途中終了も含む。同期にはイベントを使い、推定の書込み時間に依存しない。

## 測定方法の修正

前回記録のメモリDB・単発エクスポート・tracemallocと同時に測った時間・人工待機入りの数値は、今回の性能評価には使用しない。実運用相当の性能として扱う根拠が不足していたため、本記録を置き換えた。

再現例：

```sh
python scripts/benchmark_operational.py --baseline-ref 58f0dd3 --repeats 7 --db-dir scratch/bench-db --output result.json --markdown result.md
```

- 17種類の負荷、各7回。比較元と変更版を同じ環境でAB/BA交互実行し、負荷順も固定seedでシャッフル。
- 各試料は新しいプロセス・新しい実ファイルDB。初期化・データ準備は時間外。キャッシュ済み操作は準備済み、cold読取りはアプリのキャッシュのみを消去する。OS・ディスクのキャッシュは温まっている場合がある。
- 3000件の日本語を含む辞書値、読取り100000回、書込み300回。一括読取りは最大100キーを返して値を消費する1呼出しを1操作とする。値のサイズ・分布は全製品用途を代表するものではない。
- 計時とPython割当ピークは別プロセス。GCは有効。ピークは測定開始後の追加割当で、既存モデル・fixture・SQLiteネイティブ領域・RSSを含まない。
- 各測定終了後に標準sqlite3で再オープンし、全保存値を独立モデルと照合し、`integrity_check` を実行する。暗号化値は新しいNanaSQLite接続で復号照合する。
- 全件取得と分割走査は同じキー・値照合処理を計測に含む。v2受付時間とフラッシュ完了までの時間は別負荷。
- 各値の中央値・最小/最大・MAD、同じ繰返し番号の変更後/変更前比率、環境・pragma・ソース指紋をJSONに保存する。比率の中央値と中央値同士の比は一致しない場合がある。範囲は観測範囲であり信頼区間ではない。
- 既存pytestベンチの未キャッシュ読取りからrefresh時間を除外し、非同期キャッシュヒットから接続・投入・終了処理を除外した。

## 結果

全操作の表は [測定結果](benchmarks/2026-09-05-operational.md)、生データは [JSON](benchmarks/2026-09-05-operational.json) に保存した。以下は同じ繰返し同士の時間比率中央値（1未満が短縮）。

| 操作 | 時間比率 | 解釈 |
| --- | ---: | --- |
| 全キーキャッシュ済みの一括読取り | 0.736 | この条件で約26%短縮 |
| 非同期キャッシュ済み読取り | 0.926 | この条件で約7%短縮 |
| キャッシュ済み `get()` | 1.007 | ほぼ同程度 |
| キャッシュ済み `db[key]` | 1.123 | 約12%増、中央値98.2→110.2 ns。自動整合性の分岐コストが残る |
| アプリキャッシュなし読取り | 1.018 | 小差。一般的な高速化とは主張しない |
| 上限なしの非同期ファイル書込み | 1.004 | 比率範囲0.865〜1.297で変動 |

分割走査の追加Pythonピークは502932 bytes、全件取得は3721442 bytesで、この負荷では約86%削減。時間は分割走査1333 ns/行、全件取得1254 ns/行で、メモリ削減と少量の時間増加を伴う。

非同期書込みの上限なしピークは旧版1288133→変更版1732652 bytes（約35%増）。キャンセル後も投入済み処理を追跡する追加コストがある。変更版の上限16件では651475 bytesで、変更版上限なしより約62%小さい。ただし利用側が作成するコルーチン自体の上限にはならない。

自動整合性を有効にしたファイルDBのキャッシュ読取りは12688 ns/操作。既定のmanual読取りより大幅に高価で、明示オプションとする理由がある。安全性の設定を緩めて速度を稼いではいない。

300件書込みではv2完了時間などに大きな変動があり、この結果だけで回帰の大きさや高速化を断定できない。追加の3000件書込み比較も7回実施した。結果は [追加比較](benchmarks/2026-09-05-write-extended.md) と [生データ](benchmarks/2026-09-05-write-extended.json) に保存した。v2受付は比率1.106（約11%増）、フラッシュを含むv2は1.167だが範囲0.467〜2.968でなお変動が大きい。通常の挿入は1.061、更新は0.973で、こちらも観測範囲が広い。書込み全体を高速化したとは結論しない。異なる件数の試料は混ぜて集計していない。

## Actionsの比較契約

各OS/Pythonジョブで旧版と変更版を同じ依存環境・同じrunner上で実行する。PRは対象ブランチのbase SHAとPRブランチのhead SHAを直接比較する（仮マージコミットではない）。PRブランチが対象ブランチに追従していない場合、その分岐後の差も含む。pushはbefore SHA、手動実行は `baseline_ref` のタグ/コミット（空欄なら `HEAD^`）を不変のコミットSHAへ解決する。旧版ソースは別プロセスで読み込み、誤って変更版をimportしていないことも検査する。

JSON・Markdown・依存一覧をartifactに保存し、同じジョブの要約に表示する。履歴の別run同士の数値は参考扱いとし、OS/Pythonの異なる数値を同じ名前に混ぜない。pytest失敗、結果の解析失敗、壊れた集約入力を成功扱いにしない。過去タグの依存互換性は別問題で、同じ依存環境で動かない版は比較できない。

同じrunnerを使ってもバックグラウンド負荷・温度・ディスク遅延などは残る。今回はWindowsでのローカル比較であり、ActionsのLinux/macOS/Python 3.13ジョブはまだ実行していない。追加したワークフローをpushした後に確認が必要。
