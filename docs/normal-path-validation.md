# 通常経路の追加最適化と検証

2026-09-05。対象は通常のキャッシュ一括取得。dictの構造・公開API・保存形式は維持した。比較元は旧HEADではなく、この追加修正直前の作業版であり、前回の新機能・安全性修正を含む。旧版からの短縮率と加算しない。

## 調査と採用した変更

- `core.py::batch_get`：未存在キャッシュが一つでも存在すると全件ヒット用の高速経路が無効になっていた。フックなしのunbounded系に限り、既知の未存在キーを除きながら辞書内包表記で返す。正のキャッシュを先に評価する。未知のキーはKeyErrorで従来のDB/staging経路へ戻す。LRU/TTL・フックの処理は従来経路を使う。
- `async_core.py::_try_batch_get_unbounded_cache_hit`：未存在キャッシュが空なら辞書内包表記で返す。混在時は既存のtry/exceptループを維持し、辞書・未存在セットを局所変数へ取り出してキーごとの属性参照を削る。auto整合性・フック付きのexecutor経路は維持する。
- 同期と同じ内包表記を非同期の混在ケースにも使う案は、予備測定5回で約14%遅くなったため不採用。Pythonの書き方だけで優劣を断定せず、呼出経路ごとに比較した。

単発getitem/get、通常書込み、非同期受付の追跡・キャンセル・終了処理には今回の追加変更を入れていない。Rust/C++・slots・保存データの型置換も行っていない。

## 測定

## 正しさの検証

`tests/test_normal_batch_paths.py`に40ケース追加。キャッシュ準備率0/50/90/100%、既知の未存在の有無、重複キー、未存在キーをNone値として新規保存、unbounded/FIFO/LRU/TTL、非同期を確認する。フック・auto整合性・キャンセルなど既存運用試験も実行した。

最終変更後の関連105件が成功。全体結果・静的検査は末尾に記載。ベンチマーク成功時には測定中にソース指紋が変わらなかったことを検査し、終了後も最終ソースとの一致を確認した。

## 次の提案

1. 今回は限られたキー数・ミス率での結果。1/10/1000キー、未知のキーの位置、未存在率50%などへ広げて採否の適用範囲を絞る。
2. getitemの今回以前の約12ns追加コストは残っている。単純なラッパー整理を別実験として行い、クラス生成など複雑な仕組みを持ち込む前に採否を判断する。
3. 非同期書込みのFuture追跡を削る前に、投入・ロック待ち・SQLite実行を分けて測定する。今回、通常書込みを速くしたという証拠は得ていない。
